# PoC のデータ収集（証拠の出所と手順）

> PoC のカバー証拠（`seed/covers.websearch.json`）を、どう集めたかの記録。
> 本番の YouTube 収集（`src/ingest/`）とは別系統で、**「この環境から合法・確実に到達できる情報だけで、どこまで本質ランキングが組めるか」**を確かめるためのもの。

## なぜ Web 検索なのか

この PoC 環境のネットワーク方針では、youtube.com・musicbrainz.org・secondhandsongs.com・ja.wikipedia.org・歌詞サイトへの直接アクセスが遮断されている。到達できたのは、YouTube Data API（`googleapis.com`、API キーが必要）と Web 検索ツールだけだった。そこで、検索結果に現れる**歌詞データベースの「曲名/歌手名」ページ**（J-Lyric・歌ネット・UtaTen）と、**ニュース記事**を証拠として使った。歌詞データベースには商業リリースされた録音ごとにページがあるので、そのページの存在が「その歌手がその曲を録音した」証拠になる。

## 手順（全曲で同じ探索量にそろえる）

| クエリ | 内容 | 条件 |
| --- | --- | --- |
| Q1 | `j-lyric {曲名} 歌詞` | 全曲 |
| Q2 | `{曲名} {原唱者} カバー` | 全曲（原唱者なしの場合は `{曲名} {作曲者} カバー 歌手`） |
| Q3 | `歌ネット {曲名} 歌詞 カバー` | Q1+Q2 で 6 組未満のとき |
| Q4 | 英題・ローマ字題で `cover version` | 海外カバーが知られている曲（`intl`）のみ |

1 曲あたりの上限は 4 検索。**探索量が曲ごとに違うと、それ自体が順位の偏りになる**ので、手順の途中で止まった曲（`collection.json` の `complete: false`）はランキングの対象外にし、残りの手順を実行してから入れる。

## 証拠の採否

- **採る**: 検索結果のタイトルや URL が「その歌手がその曲を歌っている」ことを直接示すもの（`via: "title"`）。または、検索ツールの要約が、特定の検索結果を根拠に「この歌手がこの曲をカバーした」と明言しているもの（`via: "summary"`）。
- **採らない**: 収集者の記憶による補完（どれほど確かでも採らない）。原唱者・作家・原唱グループのメンバーによる再録（セルフカバー）。カラオケ、インスト、オルゴール、歌手名のないカバー集。**同じ曲名の別の曲**（「糸」「駅」「時代」など汎用的な曲名は、作家クレジットの一致か「○○のカバー」という明示がある場合だけ採る）。
- 各辺には証拠の URL（`src`）を付ける。要約が根拠の辺は、要約がどの結果に基づくかを明示しないことがあり、その場合 `src` は最も近い結果になる。この注記は `collection.json` の `flags` に残している。

## キュレーション（`seed/curation.json`）

収集した証拠ファイルは書き換えない。名寄せ・除外・種別の補正は `curation.json` に明示して、読み込み時に適用する。
- **表記ゆれ**: 英語ページ由来のローマ字表記を日本語表記に寄せる（例: `Kazumasa Oda` → 小田和正）。
- **除外**: 理由付きで除外する（例: 「南国土佐を後にして」の、原唱より前の録音）。
- **種別**: 歌い手・ボカロ P など、ネット発の歌い手を `net` にする。
- このほか、出典 URL のない辺（検索要約が「ファンサイトの一覧によれば」としか述べていないものなど）は、グラフ構築時に自動で除外し、件数をレポートに出す。

## 既知の限界

- **抜き取り調査である**: 1 回の検索で見えるのは 10 件前後なので、よくカバーされる曲ほど件数が頭打ちになる（実際には数十組に歌われている曲でも、ここでは 10 組前後しか見えない）。逆に、見つからなかった曲が「カバーされていない」とは限らない。
- そのため本 PoC の CoverRank は、**「何組に歌われたか」よりも「誰に歌われたか」の差**で順位が付きやすい。網羅的なデータ（YouTube Art Track、カタログ API）で置き換えるのが本番の前提になる。
- 歌い手のメタデータ（`artists.json` のデビュー年代・ジャンル・国）は、一般に知られた経歴に基づく**年代粒度の推定**である。不明なものは空欄のまま残し、推定では埋めない。本番では MusicBrainz の begin date や Wikidata に置き換える。
- 証拠の欠損が順位に与える影響は、`npm run report` のブートストラップ区間（証拠を 30% 間引いた 300 回の再計算）で確認できる。
